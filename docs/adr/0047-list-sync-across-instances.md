## Context

**SnatchArr** (meaning: automated media search-and-snatch coordinator across `*arr` instances; origin: English *snatch* + the `*arr` suffix of the Servarr ecosystem; pronunciation: `/ˈsnætʃ.ɑːr/`) already coordinates searches under per-instance hourly caps (`AGENTS.md`, Contracts). Operator direction on 2026-11-10 identifies cross-instance list syncing as a missing capability (paraphrased; ledger `snatcharr-list-sync-gap-20261110`). At baseline commit `021c2d147199`, no ADR, roadmap entry or issue covered it; the issue search on 2026-11-10 at 19:43 CET covered import lists, exclusions, watchlists and source-specific list-sync terms.

ADR-0003 imports `source=configarr` instances, re-imports linked files on change, and makes those instances read-only in the UI except for snatch policy. ## Decision

### D1. Cross-instance list controller

SnatchArr controls list definitions and exclusions across every instance of one application, called an **app group**. There is one group for each of Sonarr, Radarr, Lidarr and Readarr; Whisparr is outside this record. The applications' native import lists fetch list content. SnatchArr fans out configuration and admits list-added items into its wanted planner; it does not become a list fetcher. Sources without a native kind follow the OQ-0047-1 answer: documented MDBList and Listrr Custom List link-outs now, and a SnatchArr-served Custom List feed for one source only after a measured adopter gap.

### D2. Search-on-add off; searches use hourly caps

Every definition SnatchArr writes disables search-on-add: `ImportListResource.searchForMissingEpisodes` for Sonarr, `searchOnAdd` for Radarr, and `shouldSearch` for Lidarr and Readarr (the tagged OpenAPI contracts in References). Added items enter SnatchArr's wanted planner and are searched under the existing hourly caps and ADR-0022 priority. The cap counts searches sent per indexer, rather than HTTP requests or added titles (`AGENTS.md`, Contracts).

An unmanaged list with search-on-add enabled produces the observe finding **“list searches outside SnatchArr's caps”**. SnatchArr never edits it outside act mode. L4 must verify both the written fields and the unmanaged-list finding.

L0 must first preserve the complete writable import-list shape for each app, including every control in the [pinned field audit](#writable-import-list-field-audit), existing provider fields and explicit false versus absent values; the shared [`ProviderResource`, `arr/types.go:253–324`](https://github.com/golusoris/goenvoy/blob/arr/v2.6.2/arr/types.go#L253-L324) is insufficient. Use app-specific, presence-aware typed fields rather than raw unknown-field passthrough because exact JSON names and required-field checks make omissions explicit before the pinned mappers overwrite existing settings (the audit's contract and `ToModel` citations). A missing app-required field must produce an incomplete-read finding and prevent a definition write, never a safe default. L1 adoption waits for L0's four-app full-shape round-trip evidence and released SDK pins; L3 definition writes and L4's search-on-add tests depend on that same preservation contract.

### D3. Fan out by name; map root paths per target

One definition, keyed by name, applies to every group member. Resolve quality profiles, metadata profiles where supported, and tags by name on each target; never copy instance-local IDs between instances. For all four apps, use a SnatchArr-owned root alias mapped explicitly to one absolute path per target, then validate that path against the target's `GET /api/v3/rootfolder` (Sonarr/Radarr) or `GET /api/v1/rootfolder` (Lidarr/Readarr), using the tagged contracts in Context. Sonarr and Radarr expose a root `path`, not a name ([Sonarr resource:9–16](https://github.com/Sonarr/Sonarr/blob/v4.0.20.3014/src/Sonarr.Api.V3/RootFolders/RootFolderResource.cs#L9-L16), [Radarr resource:9–16](https://github.com/Radarr/Radarr/blob/v6.4.4.10685/src/Radarr.Api.V3/RootFolders/RootFolderResource.cs#L9-L16)); a uniform alias-to-path mapping avoids assuming identical mounts even where an app also exposes a root name. A missing or ambiguous profile, alias mapping or registered path produces a plan error and no write to that target. L0 preserves the complete per-app writable shape through target-local remapping, including Lidarr and Readarr `metadataProfileId` ([Lidarr mapper:57–66](https://github.com/Lidarr/Lidarr/blob/v3.1.6.5079/src/Lidarr.Api.V1/ImportLists/ImportListResource.cs#L57-L66), [Readarr mapper:57–66](https://github.com/Readarr/Readarr/blob/v0.4.18.2805/src/Readarr.Api.V1/ImportLists/ImportListResource.cs#L57-L66)); L3 changes only the intended definition, mapped references and D2 search flags, retaining all other writable settings. L3 tests different target mount paths, local profile IDs, preservation of non-default controls and the no-write failure paths.

### D4. One writer alongside Configarr

On a `source=configarr` instance, Configarr owns list definitions whenever its effective `import_lists.data` is nonempty or `import_lists.delete_unmanaged.enabled` is true, including empty or omitted `data` and entries covered by `ignore`. SnatchArr then writes no list definitions on that instance; it must not recreate a list Configarr intentionally pruned. Configarr's [`importListBase.ts:53–60,189–195`](https://github.com/raydak-labs/configarr/blob/v1.39.1/src/importLists/importListBase.ts#L53-L60) fetches existing lists even with empty data when pruning is enabled and deletes names outside the declared/ignored set. This conservative instance-wide boundary preserves OQ-0047-2's one-writer policy and avoids a reconciliation loop; L3 tests both declared lists and empty-data pruning. Configarr does not manage exclusions (Context), so SnatchArr may still sync exclusions there in act mode, preserving ADR-0003's ownership boundary.

Evaluate notifications independently: nonempty `notifications.data` or `notifications.delete_unmanaged.enabled` makes Configarr the sole notification writer on that instance, even with empty data or ignored names. Its [`notifications.ts:168–180,353–386`](https://github.com/raydak-labs/configarr/blob/v1.39.1/src/notifications/notifications.ts#L168-L180) reconciles and prunes notifications separately from import lists. D7 notification fan-out is refused there with an ownership finding; list ownership alone does not decide notification ownership. Unreadable effective Configarr configuration also refuses the affected writes. An ownership handoff requires the previous owner to disable its native writers and confirm that state before the new owner enables them (D7); L6 tests notification ownership, pruning with empty data and the handoff. Refusal is safer than two controllers overwriting each other's event settings (ADR-0003).

### D5. Exclusion union with observed-removal tombstones

An exclusion's identity is its app-specific foreign ID: Sonarr `tvdbId`, Radarr `tmdbId`, Lidarr `foreignId`, Readarr `foreignId` (tagged OpenAPI contracts). An exclusion observed on one member is added to the others. A removal propagates only after SnatchArr has observed that exclusion on that member and subsequently observed it gone; an initially absent exclusion is not a removal. Persist that observation history and tombstones so a simple union does not resurrect a removal. OQ-0047-3 chose this policy.

Use Radarr's bulk exclusion POST; the other apps receive single POSTs with a scalar per-tick bound. L2 must test union and tombstones for ties, empty groups, one member, and seen versus unseen removals, and prove the fake log contains only exclusion POST/DELETE calls.

### D6. Blocklist propagation through queue removal

None of the four pinned applications accepts blocklist insertion. Never replay blocklist records or write an application's database. Read each member's blocklist into deny records keyed exactly by `(app, canonicalIndexer, protocol, sourceTitle)`; use no fuzzy matching. Configure an explicit mapping from `(member ID, local indexer name)` to a group-wide canonical indexer key, for both blocklist and grab-history records; never infer equivalence from equal display names. The pinned [Sonarr `BlocklistResource`:7850–7901](https://github.com/Sonarr/Sonarr/blob/v4.0.20.3014/src/Sonarr.Api.V3/openapi.json#L7850-L7901) exposes the local `indexer` string but no release GUID or info hash. An absent or ambiguous mapping produces a finding and no queue removal, because skipping an unverified identity is safer than blocking another indexer's release. L5 tests the same indexer under different local names, unrelated indexers and missing mappings.

Add `blocklisted_elsewhere` to the ADR-0012 queue rules in `api/internal/queue/rules.go`. Obtain the original release `sourceTitle`, indexer and protocol from a grabbed-history record joined to the queue item's `downloadId` within that member, using its pinned History API; a download ID is a local join key, not a cross-instance release identity. Sonarr strips file extensions from [`QueueService.cs:60–81`](https://github.com/Sonarr/Sonarr/blob/v4.0.20.3014/src/NzbDrone.Core/Queue/QueueService.cs#L60-L81), while [`HistoryService.cs:138–169`](https://github.com/Sonarr/Sonarr/blob/v4.0.20.3014/src/NzbDrone.Core/History/HistoryService.cs#L138-L169) and [`BlocklistService.cs:74–88`](https://github.com/Sonarr/Sonarr/blob/v4.0.20.3014/src/NzbDrone.Core/Blocklisting/BlocklistService.cs#L74-L88) preserve the original release title. Do not substitute the queue's display title or strip an extension from either side. Missing, conflicting or incomplete grab history produces a finding and no removal; page reads have a scalar bound and an incomplete read cannot authorize a match (`AGENTS.md`, HISS-02). L5 tests an original `.mkv` title against its stripped queue title, missing/conflicting history and a near-miss original title.

When another member's queue item matches that exact key, removal goes through that member's `*arr` queue API with `blocklist=true`; the application creates its own blocklist entry through that allowed path. ADR-0012's observe-first, strikes and bounded-removal rules still apply, including `removeFromClient=true` and `skipRedownload=true`. There is no download-client call under ADR-0006 or ADR-0046. The cost is one started grab per member before propagation can block that release there. This refines OQ-0047-4's exact-key policy by resolving local names and original titles; L5 checks matching and the queue call in `api/internal/queue/rules_test.go`.

### D7. Two-way behaviour, with explicit limits

Collection additions use native Trakt Connect on each Sonarr/Radarr member for which D4 permits notification ownership. SnatchArr owns only notifications it created and recorded by member, notification ID and expected configuration in API Postgres; a matching name alone never grants ownership (`AGENTS.md`, Contracts; `api/internal/store/`). In act mode, set `onDownload=true` and `onUpgrade=true` on those owned notifications. On Sonarr, explicitly set `onImportComplete=false`, `onSeriesAdd=false`, `onSeriesDelete=false`, `onEpisodeFileDelete=false` and `onEpisodeFileDeleteForUpgrade=false`; on Radarr, set `onMovieAdded=false`, `onMovieDelete=false`, `onMovieFileDelete=false` and `onMovieFileDeleteForUpgrade=false`. All other mutable event flags default false. The pinned notification contracts expose those flags; native [Sonarr `Trakt.cs:36–65`](https://github.com/Sonarr/Sonarr/blob/v4.0.20.3014/src/NzbDrone.Core/Notifications/Trakt/Trakt.cs#L36-L65) and [Radarr `Trakt.cs:32–47`](https://github.com/Radarr/Radarr/blob/v6.4.4.10685/src/NzbDrone.Core/Notifications/Trakt/Trakt.cs#L32-L47) add on import and remove on local deletion independently of other members. Disabling every native deletion event is the safe shared-account policy because one remaining copy must keep its collection entry. L6 verifies exact flags per member and the remaining-copy case.

The API leader alone removes an owned collection entry through goenvoy [`RemoveFromCollection`, `trakt.go:750–752`](https://github.com/golusoris/goenvoy/blob/c8341574c82f/metadata/tracking/trakt/trakt.go#L750-L752), after fresh, complete inventory reads prove that no group member retains the movie or episode represented by that entry. Persist the collection account, foreign media identity and SnatchArr contribution before allowing removal; unowned entries and a Sonarr series with any retained collected episode are never removed wholesale (`AGENTS.md`, Contracts; `api/internal/store/`). Offline members, unknown inventory or an unmanaged delete-enabled notification sharing that account block removal and raise a finding; do not disable user-owned notifications. L6 tests one of two copies deleted, last-copy removal, an offline member and an unowned entry. Retaining an uncertain collection entry is safer than deleting shared state still backed by a member.

For source watchlists, retain Trakt `RemoveFromWatchlist` and TMDb `AddToWatchlist(watchlist=false)` as per-list opt-ins, off by default and observe first ([pinned `trakt.go:728–731`](https://github.com/golusoris/goenvoy/blob/c8341574c82f/metadata/tracking/trakt/trakt.go#L728-L731), [pinned `tmdb.go:1057–1065`](https://github.com/golusoris/goenvoy/blob/metadata/v1.4.3/metadata/video/tmdb/tmdb.go#L1057-L1065)). Before the first removal attempt, the API persists a delivery record keyed by source account/list, foreign title identity and group membership revision, with the full intended-member set, per-member admission acknowledgements and the import trigger (`AGENTS.md`, Contracts; `api/internal/store/`). An acknowledgement requires that member's API to confirm the title is in its library by foreign ID; the first import alone is insufficient. Remove only after at least one verified import and admission by every intended member, with fresh reachability and D7 cleanup checks for all of them. Native list fetches run independently ([Sonarr sync:105–115](https://github.com/Sonarr/Sonarr/blob/v4.0.20.3014/src/NzbDrone.Core/ImportLists/ImportListSyncService.cs#L105-L115), [Radarr sync:68–82](https://github.com/Radarr/Radarr/blob/v6.4.4.10685/src/NzbDrone.Core/ImportLists/ImportListSyncService.cs#L68-L82)); preserving the source entry until all admissions prevents a fast member from starving a slower one. Offline or unacknowledged members keep removal pending indefinitely with a finding, never an expiry-based waiver. Restart and retries retain acknowledgements; membership changes invalidate the removal plan and require the new intended set to be acknowledged, with no automatic shrinking of that set. L6 tests staggered polling, offline recovery, membership changes, restart and duplicate import events in `api/internal/listsync/writeback_test.go` (planned).

Before any watchlist removal, read each intended target's instance-wide `GET /api/v3/config/importlist` and allow only `listSyncLevel=disabled` or `logOnly`, refusing missing, unknown or any other value without changing it. Radarr's [`ImportListSyncService.cs:183–221`](https://github.com/Radarr/Radarr/blob/v6.4.4.10685/src/NzbDrone.Core/ImportLists/ImportListSyncService.cs#L183-L221) also accepts `keepAndUnmonitor`, `removeAndKeep` and `removeAndDelete`; the latter two remove library entries and the last deletes files. Sonarr's [`ImportListSyncService.cs:293–336`](https://github.com/Sonarr/Sonarr/blob/v4.0.20.3014/src/NzbDrone.Core/ImportLists/ImportListSyncService.cs#L293-L336) instead has `keepAndUnmonitor` and `keepAndTag`. The common allow-list preserves admitted library state when a source entry disappears. Recheck immediately before a write, and suspend pending removals with a finding when configuration becomes incompatible; L6 exercises both safe values and every rejected value, including Radarr file deletion after a title leaves its only list.

TMDb removal uses a user-authorized v3 session, not the application's read-access Bearer token alone. The pinned SDK [`tmdb.go:37–43,1057–1065`](https://github.com/golusoris/goenvoy/blob/metadata/v1.4.3/metadata/video/tmdb/tmdb.go#L37-L43) installs only application Bearer authentication and omits `session_id` from watchlist writes. L6 must extend goenvoy with session acquisition and a session-aware write, release it and bump `go.mod` before enabling TMDb removal. Follow TMDb's [session flow](https://developer.themoviedb.org/reference/authentication-how-do-i-generate-a-session-id): request a token with `GET /3/authentication/token/new`, direct the user to TMDb approval, then exchange the approved token with `POST /3/authentication/session/new`; bind the resulting session to its verified account ID and send `session_id` on [`POST /3/account/{account_id}/watchlist`](https://developer.themoviedb.org/reference/account-add-to-watchlist). Store the session encrypted at rest and expose it only as a write-only API input, following `AGENTS.md`'s secret-storage boundary; redact it from request logs. Missing, revoked or wrong-account sessions refuse removal with a finding. L6 tests the approval exchange, authenticated `watchlist=false` request, missing-session refusal and account mismatch against a fake service, never a live account.

Withdrawing act mode or a list/group's write authorization stops new source writes immediately and enters a durable notification-revocation transition. While ownership remains with SnatchArr, disable all mutable event flags on each recorded owned notification through the target API and read them back before reporting observe effective; this teardown is the only allowed configuration write during withdrawal (D10; `api/internal/store/`). Never change an unowned notification. An offline target leaves revocation pending with an explicit finding and is retried before any re-enable, including after restart. A flag update cannot cancel a notification already dispatched by the native [Sonarr service:191–207,407–423](https://github.com/Sonarr/Sonarr/blob/v4.0.20.3014/src/NzbDrone.Core/Notifications/NotificationService.cs#L191-L207) or [Radarr service:149–165,315–355](https://github.com/Radarr/Radarr/blob/v6.4.4.10685/src/NzbDrone.Core/Notifications/NotificationService.cs#L149-L165); report that in-flight limitation during withdrawal rather than promise instantaneous cessation. L6 tests imports and deletions after confirmed disable, pending revocation while offline, restart recovery and preservation of unowned notifications in `api/internal/listsync/notifications_test.go` (planned). A Plex watchlist still waits for a goenvoy plex.tv watchlist client; the local-server-only boundary remains as recorded in the SDK survey in References.

Watched/read state write-back remains outside this record. ADR-0024 reads watch state and writes none back; scrobbling stays with media-server plugins, such as the MDBList Jellyfin and Emby plugins in the survey table. Lidarr and Readarr have no write-back target in this record; that is an explicit coverage gap, not an implied fallback.

### D8. Reuse existing fetchers and ownership

Seerr requests keep their existing sync and ADR-0036 ownership. Pulsarr remains a link-out for multi-instance Plex watchlist routing. MDBList and Listrr content enters through each application's native Custom List kind where available: fan out the list URL, without calling an MDBList API. Readarr has no Custom List kind (tagged OpenAPI contract); the OQ-0047-1 answer keeps that limit.

Borrow Configarr's schema-driven reconciliation and opt-in `delete_unmanaged` design. No code is copied from GPL/AGPL projects; SnatchArr's code is EUPL-1.2 (`LICENSES/EUPL-1.2.txt`). The project survey in References informs design and link-outs, not code reuse.

### D9. Leader-only reconciliation

Register the reconciler in the fx group `leader_loops` through `gate.Provide[*T]()`, following `api/internal/snatch/module.go`. The elected API leader owns reconciliation, consistent with the existing wanted planner and ADR-0012 queue sweep.

### D10. Observe first for every write class

Definitions, exclusions, the blocklist queue rule and source write-back all default to observe per app group. Native notification fan-out follows the same boundary. Show planned writes through the API and UI; act requires explicit opt-in per group, and upgrades keep observe. Per-list source write-back additionally requires D7's opt-in, admission barrier, cleanup allow-list and authenticated account. Initial/steady observe schedules zero writes; withdrawal permits only D7's ownership-aware notification disable/read-back and stays visibly pending on unreachable members. L1–L6 must distinguish initial/steady observe from revocation, verify zero reconciler source writes during withdrawal, and verify newly triggered native import/delete events produce no writes after confirmed disable, while retaining D7's limitation for already dispatched requests (`AGENTS.md`, Contracts; L6's planned `api/internal/listsync/notifications_test.go`).

## Consequences

### Positive

- One definition and exclusion set spans each app group, with target-local profile resolution, explicit root path mappings and one writer (D1, D3–D5).
- List-added items enter the existing capped search planner rather than triggering uncapped search-on-add (D2; L4).
- Blocklist knowledge spreads through the existing queue API boundary without database writes (D6; L5).
- Native lists, goenvoy clients and Configarr's reconciliation design are reused; Seerr requests retain their existing owner (D4, D8).

### Negative

- Configarr-owned lists and notifications remain outside SnatchArr's control, including empty-data pruning policies, so those users configure two tools (D4; OQ-0047-2).
- Blocklist propagation costs one started grab per member and cannot replay an entry pre-emptively (D6).
- Readarr has no Custom List kind, and Lidarr/Readarr have no write-back target in this record (D7–D8).
- MDBList and Listrr are hosted services; link-outs require their availability and an account (OQ-0047-1).
- Reconciliation needs durable per-member observations, tombstones, admission acknowledgements and notification ownership/revocation state; uncertain or offline members delay removals (D5–D7; `api/internal/store/`).
- L0 must repair the SDK's unsupported Lidarr routes and missing typed fields; L6 must add user-session authentication before TMDb write-back can be enabled (D2–D3, D7; `go.mod`).
